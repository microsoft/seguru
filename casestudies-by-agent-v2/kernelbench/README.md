# kernelbench-gpu — KernelBench operators in SeGuRu

A from-scratch port of the KernelBench-style neural-network operator set to
SeGuRu safe Rust. All operators are `f32`, there is **no `unsafe` anywhere in the
crate**, every operator has a CPU reference implementation and a GPU-vs-CPU test,
and a benchmark binary reports kernel-only time and achieved bandwidth.

Measured on an A100-SXM4-80GB (sm_80, CUDA 13.3): elementwise kernels reach
**1.5–1.6 TB/s**, i.e. essentially the machine's STREAM-level HBM bandwidth
(~1.55 TB/s of the 2.0 TB/s peak).

## Operators

| Group | File | Operators |
|---|---|---|
| Activations | `src/activation.rs` | `relu`, `gelu` (tanh approximation), `sigmoid`, `tanh`, `swish`/`silu`, `softplus`, `leaky_relu` |
| Normalisations | `src/norm.rs` | `layer_norm`, `rms_norm`, `l1_norm`, `l2_norm` |
| Row reductions | `src/reduce.rs` | `softmax`, `log_softmax`, `sum_dim`, `mean_dim`, `max_dim`, `argmax_dim`, `cumsum` |
| Losses | `src/loss.rs` | `mse_loss` |
| Pooling | `src/pool.rs` | `max_pool1d` (arbitrary kernel size / stride) |

Support modules: `src/device.rs` (block reductions and scan built on warp
shuffles), `src/util.rs` (padding/`Float4` packing helpers), `src/testkit.rs`
(deterministic test data + tolerance assertion), `src/bench.rs` (benchmark
driver, see "Why the benchmark lives in the library" below).

Every operator group exposes three layers:

* the SeGuRu kernel(s) (`#[gpu::cuda_kernel]`),
* a host driver that pads, uploads, launches and unpads (e.g. `softmax(&x, rows, cols)`),
* an `_cpu` reference used by the tests (accumulating in `f64` where the result
  is sensitive to summation order).

## Design

### Elementwise kernels are pure bandwidth

Activations, and the elementwise stages of the norms/loss, use `Float4`
(128-bit) loads and stores with **4 `Float4` per thread** (16 elements/thread,
4096 elements per 256-thread CTA), issued as a grid-strided unrolled block so
the memory pipeline stays saturated. The host pads the buffer up to a whole
number of CTA tiles (`ELEMS_PER_CTA`), so the `reshape_map!` grid maps exactly
onto the data and the kernel contains **no tail predicate at all**.

The seven activations are generated by one `elementwise!` macro that takes the
scalar expression; the device function, the kernel, the CPU reference and the
host driver all come from the same definition, so there is no copy-paste
duplication (a weakness of the earlier port).

### Row reductions: one CTA per row + warp shuffles

Every row operator maps **one 256-thread CTA to one row** and walks the row in
`ROW_TILE = 1024`-column tiles of `Float4`. Cross-thread combination uses
`ThreadWarpTile::redux` (warp shuffles) followed by a single shared-memory
exchange between the eight warps — never a shared-memory tree over all 256
threads. `src/device.rs` provides:

* `block_reduce_sum`, `block_reduce_max` (f32, via `ReduxAdd`/`ReduxMax`),
* `block_reduce_min_i32` (i32 `ReduxMin` via hardware `redux.sync`),
* `block_exclusive_scan` (warp scan + block carry) used by `cumsum`.

All of these publish the per-warp value from lane 0 only, because of the chunk
addressing behaviour documented in limitation 2 below.

`softmax`/`log_softmax` use the **online (single-pass) algorithm**: one pass
computes `(max, sum·exp)` jointly with the rescaling merge rule, then a second
pass normalises while re-reading the row (from L2 at these sizes). The running
max is initialised to `f32::MIN` rather than `-inf`, which avoids `NaN` from
`-inf − -inf` on all-`-inf` tiles.

`argmax_dim` reduces the max first and then takes the **minimum index among the
matching lanes**, matching PyTorch's tie-break. `cumsum` does a per-thread
register scan over its `Float4`s, a block exclusive scan per tile, and carries
the block total across tiles.

`layer_norm` deliberately makes two statistics passes (mean, then variance about
that mean) instead of the cheaper but catastrophically cancelling
`E[x²] − E[x]²`; a test with a mean of 1000 and a variance of 1 covers this.

### Padding instead of predication

Host buffers are padded to `row_stride(cols)` (a multiple of the 1024-column
tile) and, for elementwise ops, to a multiple of 4096 elements. Consequences:

* the write map is always exact, so `chunk_mut` is called unconditionally at the
  top of the kernel — **`chunk_mut` never appears in divergent control flow**,
  which SeGuRu rejects with `InvalidDiversedData`;
* the only per-column predicate left (`col < cols4`) is uniform across the CTA
  and free whenever `cols` is a multiple of the tile.

`max_pool1d` clamps the *input* index instead of predicating the store, keeping
the output map exact for output lengths that are not multiples of the tile.

### `mse_loss` without atomics

Two launches: an elementwise kernel producing one partial per CTA into a device
buffer, then a single-CTA kernel that sums the partials and scales by `1/n`. No
atomics, no grid sync, and the result is deterministic run to run.

### Benchmark and probe binaries

`src/bin/bench.rs` launches the library kernels directly, in the style of
`aes/src/bin/bench.rs`. `src/bin/probe.rs` is not a benchmark: it is a standing
reproducer for the two open compiler bugs in limitation 2 below (scope-chunk
lane addressing, and `GpuShared::zero()` not zeroing).

## Findings

### Compiler bug found by this port (now fixed upstream)

**Cross-crate collision of static shared-memory globals.** Static shared buffers
were emitted as `@static_shared_N` with *external* linkage and a per-module
counter (`crates/rustc_codegen_gpu/src/context/const_static.rs`,
`define_static_shared_mem`). Linking an executable merges the bin's GPU module
with every extern crate's (`crates/rustc-gpu/src/driver.rs`,
`config_link_gpu_code`), so both defined `@static_shared_0`. `llvm-link` merges
two identically-typed external definitions silently but rejects mismatched ones,
so the failure depended purely on buffer sizes: the AES case study links because
its lib and bin globals are both `[1024 x i8]`, while this crate hit

```text
error: Linking globals named 'static_shared_0': symbol multiply defined!
```

with `[128 x i8]` in the lib versus `[1024 x i8]` in the bin. Diagnosed with
`llvm-dis` on the emitted `*.gpu.bc` modules. **Fixed upstream** by mangling the
local crate's stable crate id into the symbol
(`static_shared_{stable_crate_id:016x}_{idx}`), giving each crate its own symbol
namespace; the benchmark binary in this crate now links kernels from the library
directly, with no workaround.

**`BASE_THREAD_MASK` overflow blocking `redux.sync` at 32 lanes.**
`crates/gpu/src/cg.rs:101` computed the warp mask as
`(1u32 << Self::CHECKED_SIZE) - 1`, which overflows for `SIZE == 32`, so
`ThreadWarpTile::<32>` failed const-evaluation and the hardware `redux.sync`
path for `i32`/`u32` (`thread_mask`, `cg.rs:147`; `_redux_sync`, `cg.rs:168`)
could not be instantiated for a full warp. `argmax` originally worked around it
with a hand-written `shuffle!(xor, ...)` butterfly. **Fixed upstream** as
`u32::MAX >> (32 - Self::CHECKED_SIZE)`. `argmax_dim` now uses `redux.sync`,
which measured faster in both directions:

| argmax_dim warp stage | 1024x1024 | 4096x1024 |
|---|---|---|
| `shuffle!(xor, ...)` butterfly | 6.3 us | 13.9 us |
| `redux.sync` (`ReduxMin`) | 6.0 us | **12.8 us** |

The index is recovered without an extra pass: the row maximum is reduced first
(f32 `ReduxMax`), then each lane's candidate index is min-reduced, which is
exactly one `redux.sync` — so the instruction's value-only result costs nothing
here.

## SeGuRu limitations still open

1. **`#[gpu::device]` helpers that touch shared memory or `sync_threads` need
   `#[gpu_codegen::sync_data]`.** Otherwise `mir_analysis` assumes possible
   divergent control flow and rejects the helper with `InvalidDiversedData`.
   This also forces `#![feature(register_tool)] #![register_tool(gpu_codegen)]`
   in the crate root.
2. **Warp→block staging chunk silently misaddresses every lane but lane 0, and
   `GpuShared::zero()` does not zero.** Reproduce both with
   `cargo run --release -p kernelbench-gpu --bin probe`.
   With
   `smem.chunk_to_scope(build_chunk_scope(Block, warp), MapContinuousLinear::new(1))
   .chunk_to_scope(build_chunk_scope(warp, Thread), MapContinuousLinear::new(1))`
   — the standard "one value per warp" staging idiom — only lane 0 of warp `w`
   addresses `smem[w]`; **every other lane addresses `smem[0]`**, i.e. warp 0's
   slot. A write from, say, lane 31 (the natural place to publish an inclusive
   scan total) is therefore lost *and* corrupts warp 0's entry, with no compile
   error, no bounds check and no runtime diagnostic. This produced a wrong
   `cumsum` that looked like a rounding problem.

   256 threads (8 warps), each lane writing `100*warp + lane`, dumping `smem[0..32]`:

   | write mask | expected `smem[0..8]` | actual `smem[0..8]` |
   |---|---|---|
   | every lane | `0, 100, ..., 700` (last writer per warp) | `701, 100, 200, 300, 400, 500, 600, 700` |
   | only lane 0 | `0, 100, ..., 700` | `0, 100, 200, 300, 400, 500, 600, 700` (correct) |
   | only lane 31 | `0, 100, ..., 700` | `731, 100, 200, 300, 400, 500, 600, 700` |

   In the first row, lane 0 of each warp wrote the right slot while the other
   248 lanes raced on `smem[0]` (winner 701 = warp 7, lane 1). In the third row
   no warp total was published at all, and `smem[1..8]` still shows
   `100..700` — *stale values from the previous kernel launch*, i.e.
   `GpuShared::<[f32; 32]>::zero()` does not zero the array at run time despite
   the constructor name. That is arguably the more dangerous of the two, since
   a kernel that reads before writing sees another kernel's data.

   A reasonable diagnostic: reject (or bounds-check) an index into a chunk whose
   per-thread view has length 1 when the accessing thread's rank within the
   parent scope is non-zero, since the addressable slot count is smaller than
   the scope the chunk is derived for.
3. **Transcendentals resolve to std, not the device intrinsics.** Because the
   crate is not `no_std`, `x.exp()` picks the libm inherent method. Device code
   must call `GPUDeviceFloatIntrinsics::{exp, log, tanh, rsqrt}` through UFCS
   (wrapped here as `dexp`/`dlog`/`dtanh`/`drsqrt`).
4. **`crunchy::unroll!` must be imported by name** (`use crunchy::unroll;`); the
   path-qualified form `crunchy::unroll!{}` does not expand.
